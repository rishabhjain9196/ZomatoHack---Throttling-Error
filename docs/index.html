Where should the
workforce move?

Demand alone does not tell the whole story. Our team built a prototype that compared synthetic demand with available resource units across ten Bengaluru zones.

Our team placed third nationally.We presented the prototype to Deepinder Goyal.
Explore the prototypeView the repository

The decision loop

  1. Estimate demand for each zone.
  2. Compare demand with available supply.
  3. Show the relative pressure on a map.
  4. Let the workforce decide whether to move.

This was a team hackathon prototype, not a deployed allocation system.

Read this as a synthetic-data study. The project dates to 2019. This report reconstructs its artifacts in 2026. It does not measure real orders, fleet size, earnings or operational improvement.

03 / Test the idea

Moving supply changes both ends of the journey.

Transfer demo resource units between two zones. This arithmetic experiment keeps the total at 492 and leaves demand unchanged. It does not simulate trips or predict what drivers would do.

Scores use demand / max(resource units, 1), matching the demo. A zero-resource zone therefore uses a denominator of one. That convention prevents division by zero but is not an operational forecast.

04 / Method and engineering

What the repository contains

  • Three daily CSV profiles contain 432 rows and 4,320 synthetic demand values in total.
  • Two training CSVs each contain 4,032 rows and ten features. The notebook uses SyntheticData2.csv.
  • The SQLite snapshot defines ten zones, 492 resource units and only two driver-location records.
  • The original presentation and Android screenshot document the hackathon concept.

What the model experiment establishes

  • The Keras notebook uses a one-step look-back, ten LSTM units, 0.5 dropout and a ten-output dense layer.
  • Training uses Adam, mean absolute error, 100 epochs and a batch size of 20.
  • The notebook trains on the full constructed sequence. It contains no held-out evaluation.
  • The API reads CSV values. It does not call the saved LSTM. Model quality and current model compatibility remain unverified.

How this report was produced

  1. Read the original files. Python's csv, sqlite3 and statistics modules export the profiles, zone configuration and baseline errors. The original database is opened read-only.
  2. Align the demonstration. Normalised clock labels put each profile in time order. Zone IDs establish the same ten-column pairing used by the demo.
  3. Make comparisons explicit. Demand totals describe synthetic profiles. Scores divide demand by the archived resource configuration. Baselines use lags of one interval, one day and one week.
  4. Keep the report portable. Plain HTML, CSS, JavaScript and SVG power these charts. Pillow prepares the cached map image. There is no chart framework, live backend or tracking script.

Repairs made during the 2026 review

  • Same-zone location updates no longer increase supply. Cross-zone moves conserve resource units.
  • New drivers retain their requested ID. Invalid inputs and insufficient origin supply return explicit errors.
  • Exact clock matching replaces ambiguous substring matching. File paths no longer depend on the working directory.
  • The local CSV demo runs on Django 5.2 without loading TensorFlow. Live inference returns an explicit unsupported response.
  • The Android source now parses JSON, checks permissions, uses actual location callbacks and refreshes after a successful update.

Limits that still matter

  • Synthetic data cannot establish real demand, earnings, service quality or the value of relocation.
  • Nearest-coordinate matching ignores roads, traffic, travel time and service-area boundaries.
  • Drivers moving towards the same hotspot could create a new imbalance. This prototype does not model that response.
  • The resource weights of seven and ten are inherited demo mechanics, not individual driver counts.
  • The Android project uses a legacy Instant App toolchain. Source fixes are not a verified Android build or runtime test.

05 / Conclusion

The useful idea is the comparison, not an accuracy claim.

What this project demonstrates

  • A zone with more demand is not necessarily the zone with the greatest demand per resource unit.
  • A map can make that comparison visible while leaving the relocation decision with the workforce.
  • The reconstructed demo makes the data flow inspectable, from CSV values through API scoring to the map.

What would need evidence next

  • Real, time-aligned demand and availability data would be needed before evaluating the scoring rule.
  • A forecast should beat simple seasonal baselines on unseen real data before it supports operational decisions.
  • A relocation policy would need travel costs, capacity constraints and a controlled evaluation of service outcomes.

The achievement here is a nationally placed team prototype and a clear product experiment. The archived evidence does not support a claim of production deployment or measured business impact.
